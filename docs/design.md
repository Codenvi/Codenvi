# Codenvi - Implementation Technical Plan

Codenvi lets one person drive Claude Code on several Windows PCs from an Android phone. Each PC has several registered project folders. The phone sends a prompt to a project. The PC runs Claude Code CLI on that project, commits the result to a development branch and sends the answer back. All message content is end-to-end encrypted with a key that only the PC and the phone hold.

Codenvi is a free, open-source (MIT) project for **personal use**. Anyone can run it for themselves: host the server on their own VPS, install the Windows and Android apps from the repository, and connect them with a connection string and encryption key.

### 0.4 Personal use and distribution

- **One owner per installation.** Each person runs their own VPS, their own server and their own paired devices. There is no shared or hosted Codenvi service, and Codenvi never runs Claude on anyone else's behalf.
- **Getting started as a user** (documented in `README.md`):
  1. Rent a VPS (Ubuntu 24.04) and point a domain or subdomain at it.
  2. Add the GitHub secrets (`ENV_VARS` carries the server's name, host name and port; the keys are generated on the first deploy), and push with `[server]` in the commit message. The workflow tests the server and deploys it to the VPS (§7.7, §11.4). Then run `codenvi-admin pair` on the VPS to print the first PC connection string.
  3. Download `windows/Codenvi.exe` from the repository and run it on each Windows PC. Paste the connection string.
  4. Install Claude Code on each PC and sign in to it yourself (§4.4).
  5. Download `android/Codenvi.apk` from the repository and install it on the Android phone (allow installing from unknown sources).
  6. On the PC, press **Connect a phone** and paste the resulting string into the phone. It pairs the phone and stores the encryption key.
- Users who build from source follow `docs/building.md`.

### 0.5 Claude Code sign-in is the user's responsibility

- Installing Claude Code and signing in to it is done by the user, on each PC, outside Codenvi. Codenvi does not choose, require, configure or handle any sign-in method or credential.
- Codenvi only checks whether the `claude` CLI is present and signed in, so it can hold jobs instead of failing them (§4.4).
- Codenvi starts the unmodified `claude` binary with the environment it inherits. It doesn't add, remove or override any authentication settings.

### 0.6 Public repository and secrets

The repository is public. Secrets are never committed.

- `.gitignore` includes `*.jks`, `*.keystore`, `*.env`, `codenvi.env`, `local.properties`, `secrets.*`, `appsettings.*.local.json`, `**/bin/`, `**/obj/` and `/android/release.jks`.
- CI secrets live only in **GitHub Actions Secrets** (§11.5). The server address, SSH keys and Android signing keys are never in the code or the workflow files.
- Server secrets are never in the repository: `JWT_SECRET`, the database password and the server's password are generated by the first deploy and kept in `/var/www/<name>/shared/generated.env` (mode 600) on the VPS (§7.7). Only `ENV_VARS` is a GitHub secret.
- A **secret scan** (the `gitleaks` CLI, run directly because the action needs a license for organizations) runs on every push and pull request, and fails the build on findings.
- **GitHub secret scanning and push protection** are turned on in the repository settings.
- **Forks:** the deploy and signing steps run only when the required secrets exist (`if: env.VPS_HOST != ''` and similar), so a fork's CI builds and tests without trying to deploy or sign.
- The released `Codenvi.apk` is signed with the owner's release key. People who build their own APK sign it with their own key, and can't install it over the owner's build without uninstalling first.

## 2. System architecture

```
┌──────────────────────┐      HTTPS + WSS       ┌──────────────────────────┐      HTTPS + WSS      ┌─────────────────────────┐
│  Android app         │ ─────────────────────▶ │  VPS (Ubuntu)            │ ◀──────────────────── │  Windows desktop app    │
│  Codenvi.apk         │ ◀───────────────────── │  nginx (TLS, :443)       │ ────────────────────▶ │  Codenvi.exe            │
│  - encrypts prompts  │                         │    └▶ Codenvi server     │                        │  - decrypts prompts     │
│  - decrypts replies  │                         │       (Node.js :5080)    │                        │  - runs `claude -p`     │
│  - STT / TTS         │                         │         └▶ PostgreSQL 16 │                        │  - git branch/commit    │
└──────────────────────┘                         │            (localhost)   │                        │  - encrypts replies     │
                                                 └──────────────────────────┘                        └─────────────────────────┘
```

- **Both clients make outbound connections only.** The PC needs no open ports and no port forwarding.
- **The server is a blind relay for content.** It stores and forwards ciphertext. It knows metadata (paired installs, devices, project IDs, timestamps, job states, versions) but cannot read prompts, replies, project names, session names, commit messages or folder paths.
- **The desktop is the source of truth** for folder paths, git state and Claude session IDs. The server is the source of truth for paired installs, the device list, message history (ciphertext) and job state.
- **A PC that is offline** gets its queued jobs when it reconnects. The phone shows "Queued - device offline".

### 2.1 Trust model

- TLS protects every hop, and AES-256-GCM protects the content as well.
- Only someone with the device key can produce a valid encrypted prompt. **A compromised server or database therefore cannot inject commands into a PC**, which matters because a prompt is effectively remote code execution on the PC. The desktop rejects any job whose ciphertext fails authentication, and it also rejects replays (§5.4).
- Nothing on the server is reachable without a paired install's token, except `/health` and the rate-limited pairing endpoint.
- If the phone is lost, revoke its install from the desktop app (or with `codenvi-admin revoke` on the VPS) and rotate the device key (§5.5).

## 4. Connecting the apps to the server (single owner, no accounts)

Each Codenvi installation has exactly one owner: the person who runs the VPS. There are no users, passwords, sign-up or Google sign-in. Instead, each app install is **paired** with the server once and then authenticates as itself. Every phone and PC is a separate, individually revocable install.

### 4.1 Connection strings

A connection string is a one-time pairing code plus everything the app needs to find the server:

```
codenvi://codenvi.example.com/pair?c=<pairing code>
codenvi://codenvi.example.com/pair?c=<pairing code>&dev=<deviceId>&kv=<keyVersion>&k=<device key>   ← phone version, also carries the E2E key
```

- The pairing code is **128-bit random**, shown as Crockford Base32. It is **single-use**, **expires after 15 minutes**, and only its SHA-256 hash is stored on the server.
- The app shows the server host and asks you to confirm before pairing.
- If the VPS has no domain and uses a self-signed certificate (Q1), the string also carries `&pin=<SHA-256 of the server's public key>`. The apps then pin that key on every connection.

### 4.2 Pairing flow

0. **Host name + password (the normal way).** The owner sets `CODENVI_ACCESS_KEY` (any characters, at least 16) in the `ENV_VARS` secret. **Connect to server** in the Windows and Android apps has two fields, the server's host name and this password, entered once per device, for the phone and for any number of PCs. The apps send the password in the `code` field of `POST /pair`; the server accepts it (constant-time comparison, exactly as typed, same rate limits and failure lockout as pairing codes) instead of a one-time code and creates a separate install with its own tokens for each app, so every app is still revocable on its own. The password only authorises linking; it is not an encryption key, and the server, which knows it, cannot decrypt anything (§5). Changing it affects only new apps. A `codenvi://` string pasted into the host field still works for single-use codes.
1. **First PC without an access key:** after the first deploy, run `codenvi-admin pair --name "Home PC"` on the VPS, which prints a single-use connection string. Paste it into the desktop app's **Connect to server** screen.
2. **The phone:** on a paired PC, press **Connect a phone**. The PC asks the server for a new pairing code and shows a single string with the pairing code, the device ID and that PC's encryption key. The Windows app also shows it as a QR code: scan it with the phone (Connect screen, **Scan QR code from the PC**) or paste the string. The phone pairs with the server and stores the key in one step.
3. **More PCs:** use **Pair another PC** on any paired PC, or `codenvi-admin pair` on the VPS.
4. **Another PC's key on an already-paired phone:** that PC's **Show encryption key** gives a key-only string, `codenvi://key?dev=<id>&kv=<n>&k=<key>`.

Pairing (`POST /api/v1/pair`):

- The app sends the code, its generated install ID, its kind (desktop/android), name, app version and OS.
- The server marks the code used, creates the `installs` row and returns a refresh token plus an access token.

### 4.3 Credentials and revocation

- **Access token:** JWT, 15 minutes, signed with a server secret, carrying `iid=<install id>`.
- **Refresh token:** 256-bit random, 90 days, **rotating**. Only its SHA-256 hash is stored. Reusing an old refresh token revokes that install at once, because reuse is a sign the token was stolen, **except** when the token issued for it was never used and the rotation is less than 24 hours old: that is a refresh whose response the phone never received (network drop, app closed mid-request), so the unused token is dropped and a new pair is issued. The app therefore stays connected as long as it is opened at least once every 90 days; server deploys, restarts and app updates do not disconnect it.
- Tokens are stored with DPAPI on the PC and wrapped by the Android Keystore on the phone. They are never displayed.
- **Installs list:** both apps show every paired install (name, kind, version, last seen, IP of last use) with a **Revoke** button. An install can't revoke itself by mistake without confirming.
- **Emergency on the VPS:** `codenvi-admin installs`, `codenvi-admin revoke <id>`, `codenvi-admin revoke --all`, and `codenvi-admin pairing off|on` to block new pairings entirely.
- **Brute-force protection:** `/pair` allows 5 attempts per minute per IP, and after 20 failures in an hour it locks pairing until `codenvi-admin pairing on`. Together with the 128-bit single-use codes, guessing is not practical.

### 4.4 Claude Code on the PC (user-managed)

Installing and signing in to Claude Code is the user's job (§0.5). Codenvi only checks the state:

- At start-up and before each job, the desktop runs `claude auth status`, which exits 0 when signed in. Codenvi only looks at whether it is signed in, not at which method was used.
- If `claude` isn't on PATH, the UI shows "Claude Code CLI not found - install it and sign in, then restart Codenvi", and jobs are blocked.
- If it isn't signed in, the UI shows a red banner, "Claude Code is not signed in on this PC. Open a terminal, sign in to Claude Code, then press Retry." Jobs are held as "Waiting for Claude sign-in" and are not failed. A **Retry** button re-runs the check.
- Codenvi never opens a sign-in flow, reads credential files or stores any Claude token.

## 5. End-to-end encryption

### 5.1 Device key

- When a desktop is registered as a device, it generates a **32-byte random key** with `RandomNumberGenerator.GetBytes(32)`.
- The key is shown as **Crockford Base32** in groups of 4, plus a 4-character checksum. That is about 56 characters, easy to type and resistant to typos: `7Q2M-K9TR-…-XC4F`.
- The **Show encryption key** button re-displays the key behind a Windows Hello / Windows password check. It also offers **Copy**.
- The phone usually receives the key inside the **Connect a phone** string (§4.2), so you rarely type it.
- (Later) Show a QR code with `QRCoder` and scan it on Android. Scanning needs a camera/barcode library that isn't in the stack.
- Storage:
  - Desktop: in a local file, protected with **DPAPI** (`ProtectedData`, CurrentUser scope).
  - Android: AES-wrapped with a non-exportable **Android Keystore** key and saved in the app's private storage. One key per device.
  - **The key is never sent to the server.**

### 5.2 Key check

The server stores a **key check value** (`KCV = HMAC-SHA256(key, "codenvi-kcv-v1")[0..8]`) per device and key version. When the user enters a key on the phone, the app computes the KCV and compares it, so a typo is caught immediately. Because the key is 256-bit random, the KCV leaks nothing usable.

### 5.3 Message encryption

- Subkeys are derived with **HKDF-SHA256** from the device key: `encKey = HKDF(key, salt=deviceId, info="codenvi-v1-enc")`.
- Cipher: **AES-256-GCM**, 12-byte random nonce, 16-byte tag.
  - C#: `System.Security.Cryptography.AesGcm`.
  - Kotlin: `Cipher.getInstance("AES/GCM/NoPadding")`.
- **AAD** binds the ciphertext to its context: `"v1|" + deviceId + "|" + objectType + "|" + objectId + "|" + direction + "|" + createdAtUnixMs`. A ciphertext can't be moved to another session, swapped between prompt and response, or replayed under another ID.
- Wire format: `version(1) | keyVersion(2) | nonce(12) | ciphertext | tag(16)`, stored as `bytea` and sent as Base64.
- Plaintext is UTF-8 JSON, so fields can be added later, for example `{ "text": "...", "attachments": [] }`.
- Encrypted: prompt text, response text, progress lines, project names, session names, commit messages, CLAUDE.md contents and error details.
- Not encrypted, because the server needs them for routing and display: install IDs, device ID and name, project/session/job IDs, timestamps, job status, model alias, effort, git commit hash and app versions.

### 5.4 Replay protection

The desktop keeps the IDs of the last 10,000 executed jobs in SQLite. It refuses a job whose ID it has already seen, or whose `createdAt` is more than 24 hours old (configurable). Expired jobs are reported as `rejected_stale` rather than executed.

### 5.5 Key rotation

- **Regenerate key** on the desktop increments `key_version`, uploads the new KCV, and keeps old keys locally so its own history stays readable.
- The phone asks for the new key. Older messages stay readable on the phone only if it still holds the old version, so the app keeps all versions it was given.
- Rotation also revokes the phone's pending jobs for that device.

## 6. Database (PostgreSQL on the VPS)

### 6.1 Database security

1. Postgres listens on `localhost` only, and port 5432 is closed in `ufw`. Only the server process on the same VPS talks to it. It is the VPS's shared PostgreSQL server, and Codenvi has its own database in it.
2. Database roles:
   - The deploy creates **one** role, named like the database (the app name with hyphens as underscores), that owns the database and is used by the server and the migrations. Other databases on the shared PostgreSQL server are never touched.
3. Content is end-to-end encrypted (§5), so a database leak exposes only metadata.
4. Secrets (pairing codes, refresh tokens) are stored only as SHA-256 hashes.
5. Integration tests assert that every endpoint except `/health` and `/pair` returns 401 without a valid token, and also with a revoked install's token.

### 6.2 Schema (`src/db/schema.ts` → `drizzle/0000_init.sql`)

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;          -- gen_random_uuid()

-- One row per paired app instance (a phone or a PC). Also tracks app versions.
CREATE TABLE installs (
  id               uuid PRIMARY KEY,              -- generated by the client before pairing
  kind             text NOT NULL CHECK (kind IN ('desktop','android')),
  name             text NOT NULL,                 -- "Home PC", "Pixel 7"
  app_version      text NOT NULL,
  app_build        integer NOT NULL,
  os_version       text,
  device_model     text,
  last_ip          inet,
  paired_at        timestamptz NOT NULL DEFAULT now(),
  last_seen_at     timestamptz NOT NULL DEFAULT now(),
  revoked_at       timestamptz
);

CREATE TABLE install_version_history (
  id               bigserial PRIMARY KEY,
  install_id       uuid NOT NULL REFERENCES installs(id) ON DELETE CASCADE,
  app_version      text NOT NULL,
  app_build        integer NOT NULL,
  seen_at          timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE pairing_codes (
  code_hash        bytea PRIMARY KEY,             -- SHA-256 of the one-time code
  created_by       text NOT NULL,                 -- 'cli' or an install id
  intended_kind    text CHECK (intended_kind IN ('desktop','android')),
  expires_at       timestamptz NOT NULL,
  used_at          timestamptz,
  used_by_install  uuid REFERENCES installs(id)
);

CREATE TABLE refresh_tokens (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  install_id       uuid NOT NULL REFERENCES installs(id) ON DELETE CASCADE,
  token_hash       bytea NOT NULL UNIQUE,
  expires_at       timestamptz NOT NULL,
  used_at          timestamptz,                   -- set on rotation; reuse => revoke install (§4.3)
  replaced_by      uuid,                          -- token issued at rotation; unused => lost response, retry allowed
  created_at       timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE server_settings (
  key              text PRIMARY KEY,              -- 'pairing_enabled', 'pairing_failures', ...
  value            text NOT NULL
);

-- A desktop PC registered as an executor.
CREATE TABLE devices (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  install_id       uuid NOT NULL REFERENCES installs(id),
  name             text NOT NULL,                 -- plaintext label, e.g. "Home PC"
  key_version      integer NOT NULL DEFAULT 1,
  key_check        bytea NOT NULL,                -- KCV for current key_version
  last_online_at   timestamptz,
  created_at       timestamptz NOT NULL DEFAULT now(),
  deleted_at       timestamptz
);

CREATE TABLE projects (
  id               uuid PRIMARY KEY,              -- generated by desktop
  device_id        uuid NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
  enc_meta         bytea NOT NULL,                -- {name, devBranch}
  default_session_id uuid,
  sort_order       integer NOT NULL DEFAULT 0,
  created_at       timestamptz NOT NULL DEFAULT now(),
  updated_at       timestamptz NOT NULL DEFAULT now(),
  deleted_at       timestamptz
);

CREATE TABLE sessions (
  id               uuid PRIMARY KEY,              -- Codenvi session id
  project_id       uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  enc_meta         bytea NOT NULL,                -- {name}
  created_at       timestamptz NOT NULL DEFAULT now(),
  updated_at       timestamptz NOT NULL DEFAULT now(),
  deleted_at       timestamptz
);

CREATE TABLE messages (
  id               uuid PRIMARY KEY,              -- generated by sender (used in AAD)
  session_id       uuid NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq              bigint NOT NULL,               -- per-session ordering, assigned by server

  ip               inet,

GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO codenvi_app;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO codenvi_app;
```

`waiting_login` means the PC's Claude Code CLI isn't signed in (§4.4).

Soft deletes (`deleted_at`) are purged by a nightly server job after 30 days. "Delete session" and "clear chat" hard-delete messages immediately.

### 6.3 Schema as code (Drizzle)

- `server/src/db/schema.ts` is the source of truth. `npm run db:generate` writes a new numbered SQL file to `drizzle/` (and its snapshot in `drizzle/meta/`). Commit both. Generated files are forward-only and never edited after merge.
- Seed data (`model_catalog`, `app_min_versions`, `server_settings`) lives in `drizzle/0001_seed.sql` as `INSERT ... ON CONFLICT`. Later changes go in new migration files (`drizzle-kit generate --custom`).
- On every deploy `dist/migrate.js` (the `drizzle-orm` migrator) applies the files not yet recorded in `drizzle.__drizzle_migrations`, **before** the new release goes live. A failed migration stops the deploy and the running server stays as it was. The test suite applies every file to an empty database.
- `drizzle-orm` and `pg` stay in `dependencies` (the release bundle contains production dependencies only).
- Before migrating a database that already has data, the deploy writes a `pg_dump` to `/var/www/<name>/backups/` (last 10 kept). Nightly backups are a cron job (see `docs/self-hosting.md`).

## 7. Server (Node.js + TypeScript + Express)

### 7.1 Packages

`express` 5, `ws` (WebSockets), `pg` + `drizzle-orm` (PostgreSQL), `jsonwebtoken` (HS256 access tokens), `zod` (request validation), `express-rate-limit` and `dotenv`. ### 7.2 Request headers (version tracking)

Every request and the WebSocket handshake carry:

```
X-Codenvi-Install-Id: <uuid>
X-Codenvi-Client: android/1.4.0+42 (Android 14; Pixel 7)     | desktop/1.4.0+57 (Windows 11 26100)
```

### 7.4 WebSocket hub

`wss://<domain>/ws?token=<access>` is used by both clients. The token is re-checked on every message, and the connection closes when the token expires or the install is revoked, so the client refreshes and reconnects (or shows "This app was disconnected" if revoked).

Envelope:

```json
{ "type": "job.dispatch", "id": "uuid", "ts": 1764000000000, "payload": { } }
```

| Type | Direction | Payload |
|---|---|---|
| `hello` | client→server | `{role:"desktop"|"android", deviceId?}` |
| `job.dispatch` | server→desktop | job row + prompt ciphertext + recent session context IDs |
| `job.ack` | desktop→server | `{jobId}` → status `delivered` |
| `job.status` | desktop→server→android | `{jobId, status, startedAt?, finishedAt?, errorCode?}` |
| `job.progress` | desktop→server→android | `{jobId, sessionId, ciphertext}` (live activity line; stored as role `progress`, keeps last 200) |
| `job.result` | desktop→server→android | `{jobId, messageId, ciphertext, commitHash?}` → stored as assistant message |
| `job.cancel` | server→desktop | `{jobId}` |
| `control.request` / `control.response` | android↔desktop | Encrypted control commands (§7.5) |
| `device.presence` | server→android | `{deviceId, online}` |
| `sync.changed` | server→clients | `{entity, id}` so the other side refetches |
| `ping` / `pong` | both | Every 25 s, so proxies and NAT keep the connection |

- **Delivery guarantee:** jobs are persisted before dispatch. On every desktop `hello`, the server re-sends all `queued`/`delivered` jobs for that device in `queued_at` order. A job that stays `delivered` with no `running` status for 2 minutes is re-dispatched. The desktop dedupes by job ID.
- **Server sizing:** one Node process (one PM2 process in fork mode). Connections are kept in an in-memory `Map<installId, connection>`, which is enough for one VPS. Moving to Postgres `LISTEN/NOTIFY` would allow several server instances later.

### 7.5 Control commands (phone → desktop, encrypted)

These change state that lives on the PC, so they travel encrypted and the desktop executes them:

| Command | Effect on desktop |
|---|---|
| `session.create {sessionId, name}` | New Claude session UUID mapped to Codenvi session |
| `session.clearMemory {sessionId}` | Starts a fresh Claude session UUID for this Codenvi session (old transcript kept or deleted per setting) |
| `project.memory.get` / `project.memory.set {text}` | Read/write the project's `CLAUDE.md` |
| `project.rollback {commitHash}` | §9.3 |
| `project.status` | Branch, dirty state, last commit, running job |
| `project.changes` | The uncommitted files (path + new/updated/deleted) for the phone's Code changes page |

The response is a `control.response` with encrypted JSON. Control requests also get the replay check (§5.4).

### 7.6 Limits and hardening

- Rate limits:
  - Pairing: 5/min per IP, with the lock described in §4.3.
  - Prompts: 30/min per install.
  - General: 300/min per install.
- Message ciphertext is capped at 1 MB. Longer responses are split into multiple assistant messages by the desktop.
- Errors use the ProblemDetails format, and nothing in them echoes SQL or stack traces.
- CORS is disabled because there's no browser client.

### 7.7 VPS layout and deployment

The VPS may already host other projects (for example sites deployed with nginx, certbot, PM2 and one PostgreSQL server). **The Codenvi server must not interact with them.** Everything it creates is named from three lines of the `ENV_VARS` secret. They are not stored in the repository, so a fork or copy of it never inherits the owner's values:

```
CODENVI_APP_NAME=codenvi            # folder, PM2 process, nginx site, admin command, database + role name
CODENVI_HOST=codenvi.example.com    # public host name (also typed in the apps)
CODENVI_PORT=3005                   # local port
```

No e-mail address is used: certbot registers without one, and certificates still renew automatically.

| Item | Where |
|---|---|
| Code | `/var/www/<name>/` itself: `dist/`, `drizzle/`, `demo/`, `node_modules/`, replaced in place on every deploy (no release folders) |
| Settings and secrets | `/var/www/<name>/shared/.env` (mode 600), from `ENV_VARS` (without the three name lines) plus the generated `JWT_SECRET` and `CODENVI_ACCESS_KEY`, plus `NODE_ENV`, `PORT`, `HOST`, `CODENVI_PUBLIC_HOST`, `DATABASE_URL` |
| Process | PM2 process `<name>` (fork mode), listening on `127.0.0.1:<port>`; logs in `/var/www/<name>/logs/` |
| Database | database `<database>` owned by role `<database>`, generated password; created if it does not exist |
| Web | nginx site `/etc/nginx/sites-available/<name>` for `<domain>` (WebSocket upgrade, 1-hour read timeout), Let's Encrypt certificate for `<domain>` |
| Admin | `/usr/local/bin/<name>-admin` (`codenvi-admin`): `pair`, `installs`, `revoke`, `pairing on|off`, `purge` |

`server/deploy/deploy.sh` enforces the isolation:

- **All collision checks run before anything changes.** On the first deploy the folder, PM2 process, nginx site, database and role must not exist yet; on later deploys they must carry this app's marker or be owned by its role. The port must be free or held by this app's own process. No other nginx site may serve `<domain>`.
- Installs nginx, certbot, PostgreSQL, Node.js 20 or PM2 **only if missing**; never upgrades anything, never changes the firewall or the nginx/PostgreSQL configuration, never touches other sites, processes, databases or roles. If Node.js is older than 20 it stops instead of upgrading it.
- nginx is reloaded only after `nginx -t` passes; a rejected site file is removed again.
- Migrations run before the switch; a failed `/health` check after the switch puts the previous release back.

**Keys:** the first deploy generates `JWT_SECRET`, the database password and the server's password (`CODENVI_ACCESS_KEY`) on the VPS and stores them in `/var/www/<name>/shared/generated.env` (mode 600). Later deploys reuse them. They are never printed to the deploy log (it may be public); the server's password is read with `<name>-admin password`. A `JWT_SECRET` or `CODENVI_ACCESS_KEY` line in `ENV_VARS` overrides the generated one. To invalidate every access token, put a new `JWT_SECRET` in `ENV_VARS` and deploy again (paired apps refresh automatically).

### 8.5 Project management

- **Register:** pick a folder with the WinForms `FolderBrowserDialog`, then enter a name. Then:
  1. Check that `git` is on PATH (Git for Windows). If not, show an install link.
  2. If the folder isn't a repo, offer **Initialize git** (`git init`, `git add -A`, `git commit -m "Codenvi baseline"`).
  3. If the working tree is dirty, offer **Commit current changes as baseline** or **Stash them**. Nothing is ever discarded silently.
  4. Create and check out the dev branch: `git switch -c codenvi-dev`, or `git switch codenvi-dev` if it already exists. Record the baseline commit (kind `baseline`).
  5. Generate a project ID, upload the encrypted meta (`PUT /projects/{id}`), and create a first session named "Main".
  6. Show a reminder that Claude Code may ask to trust the folder. If a test `claude -p` run reports a trust error (V3 in §14), tell the user to open Claude Code in that folder once themselves and accept, then press **Retry**.
- **Rename:** local update plus encrypted `enc_meta` upload. It also syncs renames made from the phone.
- **Change folder path:** the new folder must be a git repo containing the dev branch, or the user re-runs steps 1–4. Claude sessions keep working because `claude --resume <id>` searches every project on the machine. The project's own CLAUDE.md and auto memory follow the folder.
- **Clear session chat memory:** per session or for all sessions in the project. It hard-deletes the server's messages (`DELETE /sessions/{id}/messages`) and gives the session a **new Claude session UUID**, so the next prompt starts with empty context. The old transcript file is deleted only if the setting is on (§8.7).
- **Delete:** removes the project from Codenvi and the server, including sessions, messages, jobs and commits records. **It never deletes the folder, the branch or commits.**

### 8.6 Job execution engine

A `JobScheduler` hosted service:

- **Queues:** one FIFO queue per project, so at most **one job runs per project** (sessions share a working tree and git index). Different projects run in parallel up to the "max parallel" setting.
- **Before a job:**
  - Decrypt and verify the prompt (§5). On failure, mark the job failed with `bad_ciphertext` and don't run it.
  - Run the replay/staleness check.
  - Check that `claude auth status` reports signed in, otherwise set `waiting_login` (§4.4).
  - Ensure the dev branch is checked out. If it isn't, fail with `wrong_branch`, unless the user enabled auto-switch.
  - Record `HEAD` as `preHash`.
- **Command line:** built with `ProcessStartInfo.ArgumentList`, so there's no shell and no quoting bugs. The prompt goes in on **stdin**, which avoids the 32k Windows command-line limit.

  ```
  claude -p
         (--session-id <uuid> -n "<session name>"   | first message in session
          --resume <uuid>)                           | later messages
         --output-format stream-json --verbose
         --model <alias> --effort <level>            | from phone dropdowns, omitted if "default"
         --permission-mode <project setting>          | default: acceptEdits
         --allowedTools <project setting list>
         --permission-prompts none                    | nobody can answer prompts → deny instead of hang
         --max-turns <project setting>
  ```

  `WorkingDirectory` is the project folder. The environment is inherited unchanged, so Claude Code uses whatever sign-in the user set up on that PC (§0.5).
- **While running:**
  - Read stdout line by line. Each line is a JSON event, parsed tolerantly (unknown types are ignored).
  - Turn tool-use events into short activity lines such as "Editing src/App.cs" or "Running: npm test", throttled to at most 2 per second, and send them as encrypted `job.progress`.
  - Capture the final `result` event's `result` text, `session_id`, cost and usage.
- **Cancel:** `Process.Kill(entireProcessTree: true)`, then status `cancelled`. Changes the agent already made stay uncommitted until the user decides (a Commit / Discard prompt in Activity). Discard runs `git restore` / `git clean` only on the user's confirmation.
- **Timeout:** 60 minutes by default (per-project setting), handled like cancel.
- **After success:** run the commit step (§9.2), then send `job.result` with the encrypted `{text, costUsd, durationMs, commitHash, filesChanged}`.
- **After failure:** send the encrypted error summary (last 30 lines of stderr). The working-tree changes stay uncommitted and are flagged in the UI.
- **Post-rollback note:** if a rollback happened since the session's last prompt, Codenvi prefixes the next prompt with a short system note, e.g. "Note: the code was rolled back to commit abc123; earlier changes discussed above have been reverted." This matters because `/rewind` is not available in `-p` mode, so the Claude conversation still "remembers" the reverted work.

### 8.7 Session ↔ Claude mapping

- A Codenvi session row stores a `claude_session_id` UUID that Codenvi generates. The first job uses `--session-id <uuid>` and later jobs use `--resume <uuid>`.
- Deleting a session, or clearing its memory with the transcript-delete setting on, deletes `~/.claude/projects/<project-dir>/<uuid>.jsonl` when that file exists. **The transcript layout is internal to Claude Code, so this is best-effort.** If the file isn't found, Codenvi just drops the mapping, and Claude Code's own 30-day cleanup removes it later.
- Codenvi sessions never touch your VS Code / interactive sessions, because they use their own UUIDs.

## 9. Git integration

All git operations use the **git CLI** (`git.exe`) through the same process runner, with `-c core.quotepath=false` and porcelain output formats.

### 9.1 Branch

- Each project has a configurable dev branch, `codenvi-dev` by default.
- Codenvi never rewrites history. It merges the dev branch into `main` and pushes `main` only when the user presses **Publish** (§9.4) - never automatically.

### 9.2 Commit after each task

```
git add -A
git diff --cached --quiet   → if no changes: record "no changes", skip commit
git -c user.name="Codenvi" -c user.email="codenvi@local" commit -m "<summary>" -m "<body>"
```

- **Summary:** the first 60 characters of the prompt (decrypted locally), prefixed with `Codenvi:`.
- **Body:** `Model: <requested alias>`, with the model id Claude Code itself resolved in parentheses when it differs from the alias; `Effort: <requested> (requested)` when an effort was requested (Claude Code never reports back which effort it actually ran at, so this is only ever what was asked for); then the first 500 characters of Claude's reply, plus trailers `Codenvi-Job: <jobId>` and `Codenvi-Session: <sessionId>`.
- If Claude made its own commits during the job, Codenvi records every commit in `preHash..HEAD` (`git rev-list --reverse`) as task commits for that job, then commits any leftovers.
- The commits are stored locally and on the server (encrypted meta, plaintext hash), and they show in both apps.
- Codenvi never commits automatically. Changes Claude leaves in the working tree stay there (this also applies when a job is cancelled, times out, or Claude Code fails), and the phone's `project.commit` command (or the desktop Activity tab's Commit button) commits them later. The commit message is exactly the text the user typed in the phone's Commit dialog, with nothing added; without text it is `"Codenvi: keep changes"`.

### 9.3 Rollback (revert, history kept)

Triggered from the desktop Commits tab or by the phone's `project.rollback` command.

1. Refuse if a job is running or the working tree is dirty, offering "commit or stash first".
2. `git revert --no-commit <target>..HEAD`, which reverts every later commit, newest first. Merge commits are not expected on this branch, but `-m 1` is applied if one is found.
3. On conflict, run `git revert --abort`. Nothing changes, and the user sees "Rollback conflicts - resolve manually".
4. `git commit -m "Codenvi: roll back to <short hash>" -m "Reverts: <list of hashes>"`. This is recorded as kind `rollback`, and the reverted commits get `reverted_by`.
5. Set the session's "post-rollback note" flag (§8.6).

Rolling forward again is the same operation targeting the commit just before the rollback commit, or a revert of the rollback commit. Both appear in the list.

### 9.4 Publish (merge to main, push)

Triggered only by the phone's `project.publish` command - there is no desktop button for it, since the phone shows a project across all its sessions while the desktop UI is per-project already.

1. Refuse if a job is running, or if the working tree is dirty (commit or discard first).
2. If the repo has an `origin` remote, `git fetch origin <main>` so the merge target is current.
3. If there is no local `main` but `origin/main` exists, create `main` tracking it; otherwise error.
4. `git switch main`, then `git merge --no-edit <devBranch>`.
5. On conflict: `git merge --abort`, switch back to the dev branch, and report "Publish conflicts - resolve manually, then push yourself." Nothing is pushed.
6. On success, `git push origin main` (skipped if there is no `origin`). A push failure is reported but the local merge is kept.
7. Always switch back to the dev branch at the end, whether Publish succeeded or failed, so the job scheduler finds the PC where it expects it.

`project.status`'s `aheadOfMain` is what the phone uses to decide whether to show the Publish button at all. After a fresh `git fetch`, with an `origin/main` it counts the commits of the dev branch (and of a local `main` that was never pushed) that `origin/main` does not have, and is 0 when the files equal `origin/main` (e.g. right after a Pull, which only adds a merge commit); without `origin/main` it is `git rev-list --count main..<devBranch>` (0 if there is no local `main`).

### 9.5 Pull (merge origin/main into the dev branch)

Triggered only by the phone's `project.pull` command.

1. Refuse if the project has no `origin` remote, if the working tree is dirty (commit or discard first), or if the PC is not on the dev branch.
2. `git fetch origin <main>`; a failed fetch is reported.
3. `git merge --no-edit refs/remotes/origin/<main>` into the dev branch.
4. On conflict: `git merge --abort` and report "Pull conflicts merging origin/main - resolve manually." The branch is left as it was.
5. On success the answer's `text` is the subject of the newest pulled commit (the tip of `origin/<main>`); older PCs answered with the new HEAD hash, which the phone ignores.

`project.status`'s `behindOrigin` (`git rev-list --count <devBranch>..origin/<main>`, 0 without `origin/main`) is what the phone uses to decide whether to show the Pull button.

### 10.4 Voice input (no paid AI API)

- Uses `android.speech.SpeechRecognizer` with `RecognizerIntent.ACTION_RECOGNIZE_SPEECH`, `EXTRA_PARTIAL_RESULTS = true`, `EXTRA_PREFER_OFFLINE = true`, and `EXTRA_LANGUAGE` from settings.
- The `RECORD_AUDIO` runtime permission is requested on first mic tap.
- The manifest needs a `<queries>` entry for `android.speech.RecognitionService` (Android 11+ package visibility).
- Partial results appear live in the message field. The final text is **inserted at the cursor** of the field, and **the app never auto-sends** - you review and edit, then press Send.
- Dictation is **continuous**: Android's recognizer always ends a session after a pause, so the same recognizer is told to listen again at once after every result or silence timeout, and each finished sentence is added to the field. It keeps going until you tap the mic button again (or send, or clear the field); after about 60 silent restarts in a row it stops by itself. The button keeps pulsing red between sentences. To make the restarts inaudible, the music, notification and system volume streams are muted while dictating and restored when it ends (so other audio is silent meanwhile); a few speech engines ignore the "wait longer" silence hints.
- If `SpeechRecognizer.isRecognitionAvailable()` is false, the mic button is hidden and a hint explains that Google speech services or an offline language pack is needed.

### 10.5 Read aloud

- Uses `android.speech.tts.TextToSpeech` with the system engine, no network or API key needed, and a `<queries>` entry for `android.intent.action.TTS_SERVICE`.
- Before speaking, Markdown is stripped and code blocks are replaced with "code block omitted".
- Text is split into chunks under `getMaxSpeechInputLength()` and queued with `QUEUE_ADD`.
- The icon toggles between play and stop, and only one message plays at a time.

### 10.6 Security on device

- Tokens and device keys are AES-GCM-wrapped by a Keystore key and stored in app-private storage.
- `android:allowBackup="false"`.
- `FLAG_SECURE` is set on the key-entry screen.
- A network security config allows cleartext only in debug builds (for a local dev server).

## 11. CI/CD (GitHub Actions)

### 11.1 One workflow, fixed order (`publish.yml`)

```yaml
on:
  push: { branches: [main] }
  workflow_dispatch:            # tick server / windows / android

jobs:
  plan:     # reads the keywords from the commit messages (or the ticked boxes) -> server, windows, android = true/false
  server:   { needs: plan,            if: plan.server }
  windows:  { needs: [plan, server],  if: !cancelled() && plan.windows && server.result in (success, skipped) }
  android:  { needs: [plan, server],  if: !cancelled() && plan.android && server.result in (success, skipped) }
```

- The keywords `[server]`, `[windows]`, `[android]` are looked for in **every commit of the push**, not only the last one.
- **Order:** the server job always runs first. The Windows and Android jobs start only after it succeeded, or straight away when `[server]` was not requested. If the server deploy fails, the apps are not built. Windows and Android then run in parallel.
- So `[server] [windows] [android]` in one commit deploys the server first, then builds both apps. Any other combination works the same way.
- Manual run: **Actions → publish → Run workflow**, tick the parts you want.
- A push without keywords starts nothing (the `plan` job only reports `false` for all three).
- Workflow permissions are read-only; only the `windows` and `android` jobs get write access, to commit their file.
- A second push waits for the running one (`concurrency` group, no cancelling).
- Bot commits that write `windows/Codenvi.exe` and `android/Codenvi.apk` contain no keywords and use `GITHUB_TOKEN`, which never triggers workflows, so they can't loop.
- **Public repo safety:**
  - Workflows run only on pushes to `main` and manual dispatch. Pull requests from forks run only `secret-scan.yml` and tests, never deploy or signing steps, and never receive secrets.
  - Commit-artifact and deploy steps are skipped in forks (`!github.event.repository.fork`), so a fork that enables Actions doesn't try to push binaries or deploy.
  - Secrets are never echoed. Steps that write key files use `umask 077` and delete them at the end of the job.

### 11.2 `windows` job

```yaml
    runs-on: windows-latest
    defaults: { run: { working-directory: windows } }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '10.0.x' }
      - run: dotnet test Codenvi.Desktop.sln -c Release
      - run: >
          dotnet publish src/Codenvi.Desktop/Codenvi.Desktop.csproj -c Release
          -r win-x64 --self-contained true -p:PublishSingleFile=true
          -p:Version=1.0.${{ github.run_number }} -o out
      - run: Copy-Item out/Codenvi.exe ./Codenvi.exe -Force   # -> windows/Codenvi.exe, size check 95 MB
      - # commit windows/Codenvi.exe (pull --rebase + push loop, skipped in forks)
```

- **Size:** a self-contained, compressed WPF+WinForms single file is roughly 70–110 MB. **GitHub rejects files over 100 MB.** The workflow fails clearly if `Codenvi.exe` exceeds 95 MB, and in that case the plan switches the file to **Git LFS** (`windows/.gitattributes: Codenvi.exe filter=lfs`). Every commit of a large binary also grows the repo permanently (Q3).
- The exe is unsigned, so Windows SmartScreen will warn on first run. The README explains this. Optional later: Authenticode signing with a certificate kept in secrets.

### 11.3 `android` job

```yaml
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '17' }
      - uses: gradle/actions/setup-gradle@v4
      - name: Decode keystore
        if: github.repository_owner == 'Irakli Gzirishvili'
        run: |
          umask 077
          echo "${{ secrets.ANDROID_KEYSTORE_B64 }}" | base64 -d > android/release.jks
      - working-directory: android
        run: ./gradlew testReleaseUnitTest assembleRelease -PversionCode=${{ github.run_number }}
        env:
          KEYSTORE_PATH: release.jks
          KEYSTORE_PASSWORD: ${{ secrets.ANDROID_KEYSTORE_PASSWORD }}
          KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
          KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
      - run: cp android/app/build/outputs/apk/release/app-release.apk android/Codenvi.apk
      - name: Remove keystore
        if: always()
        run: rm -f android/release.jks
      - # commit android/Codenvi.apk like the Windows step (skipped in forks)
```

- **Signing is required** in the owner's repository: `ANDROID_KEYSTORE_B64` and `ANDROID_KEYSTORE_PASSWORD` (alias `codenvi`, key password = store password; `ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD` only if you chose other values). The build fails without them instead of producing a debug-signed APK, and it refuses to publish an APK whose signing certificate differs from the one in the committed `android/Codenvi.apk`. This is what lets each new APK install over the old one, so the app keeps its pairing and keys.
- The release keystore must stay the same forever. Otherwise installed apps can't update. Generate it once and back it up outside GitHub. It is never committed (`*.jks` is in `.gitignore`).

### 11.4 `server` job

1. Reads and validates the three server settings from the `ENV_VARS` secret (`.github/scripts/read-server-settings.js`); forks skip this step and the deploy.
2. `npm ci`, type-check, `npm test` against a `postgres:16` service container (every migration from zero, REST + WebSocket suite), `npm run build`.
3. Bundles `dist/`, `drizzle/` and production `node_modules` into `release.tgz` (a few MB; nothing else from the repository is uploaded).
4. Copies the bundle, `server/deploy/deploy.sh` and `ENV_VARS` over SSH to a private temp folder on the VPS and runs `deploy.sh` as root (`sudo` when `VPS_USER` is not root). The script deletes the upload when it ends. The VPS host key is taken with `ssh-keyscan` on each run.
5. Checks `https://<domain>/health`.

Rollback is a `git revert` and a new `[server]`. Migrations are forward-only, so keep them backward-compatible with the previous release (expand/contract), because a failed health check switches the code back but not the database.

### 11.5 Required secrets and variables

Stored only in **GitHub → Settings → Secrets and variables → Actions** of the owner's repository.

| Name | Used by |
|---|---|
| `VPS_HOST`, `VPS_USER`, `VPS_SSH_PRIVATE_KEY`, `ENV_VARS` | server (required) |
| `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD` | android (required, see §11.3); `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` only for a non-default alias/key password |

The server address is not baked into the builds. It comes from the connection string at pairing time, so the same `Codenvi.exe` and `Codenvi.apk` work with any user's server.

`ENV_VARS` holds the three lines that name the server (and optional overrides, see `server/.env.example`). The deploy writes the effective settings and the generated keys to `/var/www/<name>/shared/.env`.

## 14. Verifications to do early (assumptions about Claude Code CLI)

These are based on Claude Code's current docs. Verify each on a real PC in Phase 4, before building on it:

## 15. Open questions for you

- **Q1. Domain.** HTTPS with automatic certificates needs a domain or subdomain pointing to the VPS, e.g. `codenvi.yourdomain.com`. Do you have one? (A bare IP would need a self-signed certificate pinned in both apps, which is possible but clunkier.) The same applies to every user who self-hosts.
- **Q2. Deploy tags.** `[android]`, `[windows]` and `[server]` in any commit of the push, in any combination.
- **Q3. Binaries in git.** Committing `windows/Codenvi.exe` and `android/Codenvi.apk` on every build makes the repo grow by around 100 MB per desktop build, and every clone of the public repo downloads that history. Options: keep it as asked (with Git LFS for the exe), or additionally attach each build to a GitHub Release and keep only the latest in root. Releases are also the usual place users look for downloads.
- **Q4. Permission defaults.** Codenvi runs Claude Code with nobody at the PC. The default plan is `acceptEdits` plus an allowed-tools list per project, with anything else denied. Do you prefer a stricter default (read-only until you allow tools) or a looser one (`bypassPermissions`, which is riskier)? A later phase could forward each permission prompt to the phone for approval through `--permission-prompt-tool`.
- **Q5. Copyright holder.** Which name should appear in the MIT `LICENSE` copyright line: your personal name, or a handle?
- **Q6. Android application ID.** `app.codenvi` assumes nobody else uses it on the Play Store. If you own a domain, a reverse-domain ID based on it (e.g. `com.yourdomain.codenvi`) is safer. It can't change after the first release.
