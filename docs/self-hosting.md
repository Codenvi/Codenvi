# Self-hosting the Codenvi server

One server per person. It relays ciphertext between your phone and your PCs and stores message history, which it cannot read. The server lives in `server/` (Node.js, TypeScript, Express, PostgreSQL via Drizzle). Pushing a commit with `[server]` in its message tests it and deploys it to your VPS.

## 1. What you need

- A Linux VPS (Ubuntu/Debian) with SSH access as `root`, or as a user with password-less `sudo`.
- A DNS **A record** for the server's host name (for example `codenvi.example.com`) pointing at the VPS, and ports 80 and 443 open.
- Your own GitHub repository (a fork or copy of this one) with Actions enabled.

The VPS may already run other projects. The deploy uses the nginx, certbot, PostgreSQL, Node.js and PM2 already installed there; it installs any of them only if missing, and never upgrades or reconfigures them.

## 2. Name your server (nothing in the repository)

The server's name, host name and port are **not stored in the repository**. They are three lines of the `ENV_VARS` secret (section 3), so a fork or copy of this repository never inherits your values, and nothing about your server appears in the code.

| `ENV_VARS` line | Meaning |
|---|---|
| `CODENVI_APP_NAME=codenvi` | Folder `/var/www/<name>` on the VPS, PM2 process `<name>`, nginx site `<name>`, admin command `<name>-admin`, and the PostgreSQL database and role (hyphens become underscores, so `my-app` uses `my_app`). 2-40 lowercase letters, digits or hyphens, starting with a letter. |
| `CODENVI_HOST=codenvi.example.com` | Public host name of the server. nginx serves it and gets a Let's Encrypt certificate for it. This is also the **Host name** you type in the apps. |
| `CODENVI_PORT=3005` | Local port the server listens on (127.0.0.1 only; nginx proxies to it). 1024-65535. Pick one that no other project on the VPS uses. |

That is everything you have to choose. No e-mail address is needed (certificates are requested without one and renew automatically; you just don't get an expiry warning e-mail if a renewal ever fails), and the keys are generated for you (section 3).

## 3. GitHub secrets

Repository → **Settings → Secrets and variables → Actions**. Four secrets for the server:

| Secret | Value |
|---|---|
| `VPS_HOST` | IP address or host name of the VPS. |
| `VPS_USER` | SSH user: `root`, or a user with password-less `sudo`. |
| `VPS_SSH_PRIVATE_KEY` | A private key whose public key is in that user's `~/.ssh/authorized_keys` (see below). |
| `ENV_VARS` | The three lines from section 2, one `KEY=VALUE` per line. Optional extra lines are listed in `server/.env.example`. |

**Keys you do not have to create.** On the first deploy the server generates, on the VPS, a `JWT_SECRET` (signs the sign-in tokens), the database password, and the server's password (`CODENVI_ACCESS_KEY`, see section 4a). They are stored in `/var/www/<name>/shared/generated.env` (mode 600), reused by every later deploy, and never printed to the deploy log. If you prefer to choose `JWT_SECRET` (at least 32 characters) or `CODENVI_ACCESS_KEY` (at least 16), add them to `ENV_VARS`; yours win over the generated ones.

The Android app needs its own two secrets, `ANDROID_KEYSTORE_B64` and `ANDROID_KEYSTORE_PASSWORD` ([docs/building.md](building.md#android-signing)); they cannot be generated by the deploy, because the signing key must stay the same forever.

A key for the deploy:

```bash
ssh-keygen -t ed25519 -C "codenvi-deploy" -f ~/.ssh/codenvi_deploy
cat ~/.ssh/codenvi_deploy.pub | ssh <user>@<vps> "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys"
# then paste the contents of ~/.ssh/codenvi_deploy (the private key) into VPS_SSH_PRIVATE_KEY
```

`NODE_ENV`, `PORT`, `HOST`, `CODENVI_PUBLIC_HOST` and `DATABASE_URL` are written by the deploy from the three settings and the generated database password. If `ENV_VARS` contains them, they are ignored, and the three `CODENVI_APP_NAME`, `CODENVI_HOST`, `CODENVI_PORT` lines are not copied into the server's `.env` either.

## 4. Deploy

```bash
git commit -am "Update server [server]"
git push origin main
```

Or run **Actions → publish → Run workflow** and tick **server**. The `server` job of `.github/workflows/publish.yml`:

1. Reads and validates the three settings from `ENV_VARS` (forks skip this and the deploy).
2. Installs, type-checks, runs the server tests against a fresh PostgreSQL (every migration from zero), builds.
3. Bundles the build with its production dependencies and uploads it, with `server/deploy/deploy.sh`, to the VPS.
4. `deploy.sh` runs on the VPS as root:
   - **Collision checks first** (nothing has been changed yet). It stops if the folder, PM2 process, nginx site or database/role of that name belongs to another project, if the port is used by another process, or if another nginx site already serves the host name.
   - Generates `JWT_SECRET`, the database password and the server password on the first deploy (reuses them afterwards).
   - Creates the database role and database (named after the app) if they do not exist, and keeps the role's password in sync with the stored one.
   - Writes `/var/www/<name>/shared/.env` (mode 600).
   - Unpacks the new code into a staging folder, backs up the database (`pg_dump`, if it has tables), and applies new migrations from there. If a migration fails, it stops and the running server is untouched.
   - Replaces the code in `/var/www/<name>/` in place (`dist/`, `drizzle/`, `demo/`, `node_modules/`) and restarts PM2 process `<name>`. If `/health` does not answer within 30 s, the deploy fails (there is no automatic rollback).
   - Writes nginx site `<name>` (WebSocket-ready), tests the nginx configuration before reloading, and gets or attaches the Let's Encrypt certificate for the host name.
   - Installs `/usr/local/bin/<name>-admin`.
5. Checks `https://<domain>/health` from GitHub.

## 4a. Connect the apps (host name + password, no command to run)

The server has one **password** (`CODENVI_ACCESS_KEY`). You can choose it or let the deploy generate it:

- **Generated (nothing to do):** the first deploy creates a random 24-character password. Read it once on the VPS, as root or with `sudo`:
  ```bash
  codenvi-admin password          # <name>-admin password
  ```
  It is not shown in the GitHub deploy log, so a public repository never exposes it.
- **Chosen by you:** add `CODENVI_ACCESS_KEY=<your password>` to `ENV_VARS` (at least 16 characters, any characters allowed; for example `node -e "console.log(require('crypto').randomBytes(18).toString('base64url'))"`) and deploy.

After the deploy, **Connect to server** in the Windows app and in the Android app has two fields. Type them once on each device:

| Field | Value |
|---|---|
| Host name | `CODENVI_HOST`, for example `codenvi.example.com` (not the bare domain `example.com`). `https://` and a trailing `/` are ignored. |
| Password | the `CODENVI_ACCESS_KEY` value |

There is no limit on the number of PCs, and the password does not expire.

- **Each app gets its own credential.** Linking creates a separate install for every app (visible in the apps under Settings, or with `codenvi-admin installs`). Revoking one install, from any linked app or on the VPS, cuts only that app off.
- **The password does not read anything.** It only decides who may link to your server. Messages are end-to-end encrypted with per-PC keys that never leave your PCs and phone (the PC's **Connect a phone** or **Show encryption key** hands a PC's key to the phone). The server knows the password but not those keys.
- **Changing it.** If the password leaks, put a new `CODENVI_ACCESS_KEY` line in `ENV_VARS` and deploy again. Apps already linked keep working, because they hold their own credentials; new apps need the new password. Revoke any install you do not recognise.
- **Wrong password:** counted as a failed attempt: 5 per minute per address, and after 20 failures in an hour new linking is switched off until `codenvi-admin pairing on`.
- **Without a password set**, the server still works: create single-use strings on the VPS with `codenvi-admin pair --name "Home PC"` (valid 15 minutes, paste the string into the *Host name* field), or use **Pair another PC** in a linked PC app.

## 5. What the deploy never does

It never changes the firewall, runs `apt upgrade`, upgrades Node.js, edits PostgreSQL or nginx configuration, touches other nginx sites, other PM2 processes, other databases or roles, or anything outside `/var/www/<name>`, `/etc/nginx/sites-*/<name>`, the certificate for `<domain>` and `/usr/local/bin/<name>-admin`. nginx is only reloaded after `nginx -t` passes. If Node.js on the VPS is older than 20, the deploy stops rather than upgrading it.

## 6. Admin commands

```bash
codenvi-admin pair --name "Laptop"        # single-use connection string (only needed without an access key)
codenvi-admin pair --kind android         # phone string without a key (add keys on the phone later)
codenvi-admin installs                    # paired apps, versions, last seen
codenvi-admin revoke <install-id>         # cut one app off
codenvi-admin revoke --all                # emergency: cut everything off
codenvi-admin pairing off|on              # block / allow new pairings (auto-off after 20 failures/hour)
codenvi-admin purge                       # run the nightly cleanup now
pm2 logs codenvi                          # server logs (also /var/www/codenvi/logs/)
```

To sign every app out of its current access token, put a new `JWT_SECRET` line (at least 32 random characters) in `ENV_VARS` and deploy again; the apps refresh automatically.

Lost phone: revoke it here or from a PC, then **Regenerate key** on every PC (Settings) and give the new keys to your other phone.

## 7. Backups and restore

Before migrating a database that already has data, every deploy writes `/var/www/<name>/backups/pre-<release>.sql.gz` (last 10 kept). For a nightly dump add (as root):

```bash
cat > /etc/cron.d/codenvi-backup <<'CRON'
15 3 * * * root runuser -u postgres -- pg_dump codenvi | gzip > /var/www/codenvi/backups/nightly-$(date -u +\%Y\%m\%d).sql.gz && find /var/www/codenvi/backups -name 'nightly-*.sql.gz' -mtime +14 -delete
CRON
```

Copy the dumps off the VPS regularly. Content is end-to-end encrypted, but metadata (device names, timestamps) is not.

Restore:

```bash
pm2 stop codenvi
runuser -u postgres -- psql -c "DROP DATABASE codenvi" -c "CREATE DATABASE codenvi OWNER codenvi"
gunzip -c /var/www/codenvi/backups/<file>.sql.gz | runuser -u postgres -- psql -d codenvi
runuser -u postgres -- psql -d codenvi -c "REASSIGN OWNED BY postgres TO codenvi"
pm2 start codenvi
```

## 8. Rollback

Revert the commits and push again with `[server]`. Migrations are forward-only, so keep them backward-compatible with the previous release (add columns before using them, remove them a release later). The VPS keeps no older copies of the code; the database backups made before each deploy are in `/var/www/<name>/backups/`.

## 9. Removing the server from the VPS

```bash
pm2 delete codenvi && pm2 save
rm -f /etc/nginx/sites-enabled/codenvi /etc/nginx/sites-available/codenvi && nginx -t && systemctl reload nginx
certbot delete --cert-name codenvi.example.com
runuser -u postgres -- psql -c "DROP DATABASE codenvi" -c "DROP ROLE codenvi"
rm -rf /var/www/codenvi /usr/local/bin/codenvi-admin
```

## 10. No domain? (self-signed + pinning)

A real domain with Let's Encrypt is the supported path. With a bare IP, terminate TLS yourself with a self-signed certificate, then compute its pin:

```bash
openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform der \
  | openssl dgst -sha256 -binary | base64 | tr '+/' '-_' | tr -d '='
```

and add `CODENVI_PIN=<pin>` to `ENV_VARS`. Connection strings then carry `&pin=…`, and both apps accept only that exact key.

## 11. Troubleshooting

| Symptom | Check |
|---|---|
| `[stopped] ... already exists` / `belongs to another project` | Your `ENV_VARS` names something another project uses. Pick another `CODENVI_APP_NAME` (the database is named after it), `CODENVI_PORT` or `CODENVI_HOST`. |
| `ENV_VARS needs CODENVI_...` | One of the three settings is missing or malformed (section 2). The message says which. |
| `Missing repository secrets` | Add the listed secrets (section 3). |
| `JWT_SECRET in ENV_VARS must be at least 32 characters` | Make it longer, or remove the line: the deploy generates one. |
| I do not know the server's password | Run `codenvi-admin password` on the VPS (or set `CODENVI_ACCESS_KEY` in `ENV_VARS`). |
| Server stops with `CODENVI_ACCESS_KEY must be at least 16 characters` | Choose a longer password (section 4a). |
| App says the host name or password is wrong | The host name must be exactly `CODENVI_HOST`; the password must equal `CODENVI_ACCESS_KEY` (case-sensitive). Or linking was locked after repeated failures: `codenvi-admin pairing on`. |
| `sudo: a password is required` | `VPS_USER` needs password-less sudo, or use `root`. |
| Health check fails | `pm2 logs codenvi`; the deploy has already switched back to the previous release. |
| Certificate warning | The DNS A record does not point at the VPS yet. Fix it and push again. |
| Phone says "Queued - device offline" | The PC app is not connected; `curl https://<domain>/health` must answer. |

## 12. Files on the VPS

| Path | What |
|---|---|
| `/var/www/<name>/dist/`, `node_modules/`, `drizzle/`, `demo/` | the running code, replaced in place on every deploy |
| `/var/www/<name>/shared/.env` | secrets and settings (mode 600) |
| `/var/www/<name>/shared/generated.env` | the keys the deploy generated: `JWT_SECRET`, database password, server password (mode 600; keep it, deleting it makes the next deploy generate new ones) |
| `/var/www/<name>/logs/` | server logs |
| `/var/www/<name>/backups/` | database dumps taken before migrations |
| `/var/www/<name>/ecosystem.config.cjs` | PM2 definition (written on each deploy) |
| `/etc/nginx/sites-available/<name>` | the server's nginx site |
| `/usr/local/bin/<name>-admin` | admin command |
